# Spec: models

Lean model access is the first engine-core piece. This amendment must land on
main before its implementation tickets start.

## Problem Statement

Users need to change model providers without losing usable conversation history,
tool calls or visibility into failures and spending. Client and extension authors
need one predictable contract instead of repeating provider-specific streaming,
authentication and cancellation. Development must work without credentials or
paid requests. Model access must not become a credential store, catalog network
controller or session runtime.

## Solution

Maestro supplies one model interface with consistent messages, streaming events,
usage and failures. Registered adapters support chat and four additional native
operations: classification, image generation, embeddings and reranking. One
configurable chat-completions connection ships with the core; extensions can
supply other adapters without changing callers.

The model module owns dispatch, projection and result normalization. It accepts
selected-provider request authentication through a small injected interface.
The application owns selection, local settings/catalog composition and visible
retries; the credential owner handles credential lifecycle; the extension host
admits registrations and hooks. A scripted fake exercises the same interface
before live transport is connected.

## User Stories

### Select and understand a model

1. **US01.** As a user, I want to choose a configured provider and model, so that I control where my conversation is sent.
2. **US02.** As a user, I want consistent text, image, thinking and tool-call content with safe conversation projection, so that I can change providers without rewriting history.
3. **US03.** As a user, I want supported thinking levels and predictable output defaults, so that the effective request reflects my choice without sending unsupported values.
4. **US04.** As a user, I want explicit model/thinking changes saved and session choices restored without rewriting startup defaults, so that changing a preference and resuming work remain distinct actions.
5. **US05.** As a user, I want truthful usage, estimated cost, retry progress and cancellation, so that I can understand spending and stop waiting.

### Configure and extend access

6. **US06.** As a team lead, I want local model catalogs and defaults composed through layered settings, so that customization respects settings locks.
7. **US07.** As an extension author, I want to register declared model operations, so that callers can use a new provider without modification.
8. **US08.** As an extension author, I want cancellable, selected-provider request authentication, so that model access does not own or expose the credential store.
9. **US09.** As a user, I want local catalog lookup and reversible overrides without network discovery, so that configured choices remain available offline.
10. **US10.** As a client author, I want one event and failure contract, so that built-in and extension adapters behave consistently.

### Reuse the model seam

11. **US11.** As an agent, I want structured classification of supplied state, so that I receive typed answers rather than parsing conversational text.
12. **US12.** As an agent, I want native image generation, so that image-producing capabilities reuse ordinary model access.
13. **US13.** As an agent, I want embeddings for ordered text inputs, so that knowledge capabilities can represent text without owning inference.
14. **US14.** As an agent, I want scores for a query and candidate documents, so that retrieval can reorder candidates without owning inference.
15. **US15.** As a client author, I want deterministic scripted responses and failures, so that I can test without credentials or paid requests.

## Implementation Decisions

### D01 — One deep model module

`maestro-models` invokes registered models. Its interface exposes registration,
local lookup, chat streaming/completion and the four native non-chat operations.
Completion consumes the same stream; it never dispatches a second request.
An advertised model is callable only when its adapter implements its operation.

Provider adapters hide wire conversion. The scripted fake and configurable
chat-completions adapter are two replaceable adapters at the same model seam.
The network adapter accepts an injected transport, with production HTTP and
scripted transport implementations. Request authentication and cancellation
are supplied, not discovered through an ambient application singleton.

The models crate has no internal workspace dependency. It imports no application,
frontend, credential store, extension host, MCP or jobs crate. Keep projection,
options and accounting as cohesive private modules, not forwarding crates.
Removing the network adapter must leave fake requests working. Removing
credential persistence or application catalog loading must not prevent an
explicitly registered, explicitly authenticated request. Removing the model
module would otherwise force normalization and stream invariants into callers;
that is the behavior this deep module earns its place by hiding.

### D02 — Registry and model identity

Identity is provider ID, model ID and operation. Provider IDs, model IDs,
endpoints and capabilities are data, not closed provider rosters. Entries carry
display name, protocol, endpoint, input capabilities and flat price metadata.
Chat entries add context/output limits, reasoning support and optional thinking
mappings. Classifier, image, embedding and reranking entries describe only the
capabilities and operation-specific limits their adapters actually support.

Known-model lookup reads locally registered data without network or credential
resolution. Available-model lookup additionally uses configured-auth status and
provider account filtering; it neither refreshes credentials nor runs credential
commands and is not a promise that a live request will succeed. A failing local
catalog getter contributes no entries and reports a diagnostic without erasing
other providers. Chat lookup excludes non-chat operations.

Model metadata is not an image-processing policy. No request-byte/image-count
limits, resize profiles, generic sampling overlays or remote freshness fields
are introduced by this contract. A dispatched request captures its adapter and
metadata; subsequent registration changes cannot rewrite it.

### D03 — Selection belongs to the application

Explicit selection wins. Otherwise a new session uses its first scoped model,
then its saved default, then an available provider-default model, then the first
available model. A resumed session first tries its recorded selection. Failed
restoration reports the reason and fallback. Provider defaults are data, not
branches naming providers.

Selection supports explicit provider/model references, exact IDs, name/ID
matching, scoped patterns and a thinking suffix. Match a full ID before parsing
its final colon as thinking; slashes and colons can belong to IDs. For duplicate
exact IDs, use the sole configured provider or report ambiguity. Fuzzy matching
prefers an undated alias, then the latest sorted dated ID. Scoped patterns
report unmatched entries and deduplicate matches.

An explicitly identified known provider may supply base metadata for an unlisted
model ID, with a visible custom-ID warning rather than a claim of catalog
verification. Unknown providers or unresolved unqualified selections fail.

An explicit model change verifies configured authentication, records the session
choice and normally persists the provider/model startup default, subject to
settings locks. Thinking is re-clamped to the new model. An effective thinking
change is recorded and normally persists the global default, except that a
non-reasoning model forcing `off` does not erase the user's reasoning preference.
Session restoration does not perform these preference writes. There is no
per-model thinking preference store or separate persist-only opt-in default.
These are application behaviors, not implementation work inside model tickets.

### D04 — Messages and plain provider projection

Request context consists of a separate optional `systemPrompt`, ordered
`messages` and current `tools`. Messages are user, assistant and tool-result
records with millisecond timestamps. The system prompt and tools are current
request inputs, not incremental system messages in the transcript.

User and tool-result content supports text and base64 images with MIME types.
Assistant content supports text, thinking and tool calls. Tool calls carry ID,
name, JSON-object arguments and optional opaque replay metadata. Tool results
retain call ID, tool name, text/image content, optional JSON details, error state
and timestamp. Details are application data, not automatically provider content.
Tool declarations contain only name, description and JSON Schema parameters;
execution callbacks and execution policy belong elsewhere. Models expose a pure
function for schema validation/coercion of tool-call arguments against these JSON
Schema parameters; the agent calls it before execution hooks.

Assistant messages retain requested provider/protocol/model, timestamp, content,
flat usage, terminal reason and useful failure text, with optional actual response
model and response ID. Requested/effective thinking is visible through request
resolution, not new mandatory serialized assistant fields. Redacted thinking is
opaque, never readable text.

Projection retains supported same-model replay metadata. Foreign signatures are
removed; foreign redacted thinking is dropped; readable foreign thinking becomes
text. Tool-call IDs are rewritten consistently with their results. Unsupported
images become explicit omission text. Missing tool results, including trailing
or interrupted calls, receive synthetic error results. Failed/aborted assistant
attempts do not become completed turns in outgoing context. Projection never
mutates authoritative history, its images or the supplied prompt/tools.

There is no system/tool-change replay, named-section delta, constrained-sampling
negotiation, nested tool-call record or tool-result usage field in model records.

### D05 — Streaming, failures and cancellation

Success emits one `start`, balanced content-block start/delta/end events, and
exactly one `done`. Families are text, thinking and toolcall; interleaved blocks
are associated by content index. Empty successful responses still have start
and done. Earlier retained events are owned snapshots: later content or usage
updates cannot mutate them.

Text/thinking start empty and grow through deltas; redacted thinking may arrive
complete without deltas. Unicode survives fragmentation. Tool arguments may be
incomplete during deltas but must be a JSON object at `toolcall_end`. A partial
tool call is not executable.

The event payloads are `start { partial }`; block starts
`{ contentIndex, partial }`; deltas `{ contentIndex, delta, partial }`;
text/thinking ends `{ contentIndex, content, partial }`;
`toolcall_end { contentIndex, toolCall, partial }`;
`done { reason, message }`; and `error { reason, error }`, with the terminal
assistant message in `error`. Each event includes its `type`.

Success reasons are `stop`, `length` and `toolUse`. Failure reasons are `error`
and `aborted`. A setup failure may emit error without start; failure after start
preserves valid partial content and usage, then emits error. Nothing follows a
terminal event. Pending and deferred are not terminal reasons or model features.
Provider/auth/setup failures, including failures before a stream is constructed,
use this same contract rather than escaping or panicking. Distinguish capability,
authentication, malformed/incomplete stream, transport/status, quota/billing and
context-overflow failures where callers need different recovery. Public failure
text and diagnostics exclude secrets.

For the bundled chat connection, success requires a recognized non-null upstream
finish reason mapped to a success reason. Clean EOF after that reason succeeds,
with or without `[DONE]`; a marker alone is not a finish reason. EOF or `[DONE]`
without a recognized finish reason is an incomplete-stream failure, never an
implicit stop. Malformed data or a transport error still fails even if a finish
reason was seen. An answer cut short must not look complete. Usage-only trailers
before EOF or the end marker are retained. Unknown finish reasons fail clearly.

Cancellation reaches authentication waits, transport setup, stream reads, hooks
and retry sleeps. It yields one aborted outcome, is never retried, and stops local
waiting/work without claiming that remote work has been undone.

The agent wraps a model update as
`message_update { message, assistantMessageEvent }`. JSON/RPC serializes the
cumulative outer message and nested partial snapshots; it does not replace them
with a delta-only representation. Model events remain separate from agent events.
Application events such as `thinking_level_changed`, `auto_retry_start` and
`auto_retry_end` are owned by the application, not emitted by model dispatch.

### D06 — Thinking and request options

Levels are `off`, `minimal`, `low`, `medium`, `high` and `xhigh`. Non-reasoning
models expose only off. Explicitly disabled mappings stay disabled; xhigh
requires explicit support. An unsupported request chooses the next supported
higher level, otherwise the nearest lower level. The application composes
explicit/scoped effort with the global startup default; models receive that
choice and expose the effective result without reading settings.

Simple chat requests use an explicit output limit unchanged, or otherwise the
smaller of a positive model output limit and 32,000 tokens. If the model has no
positive output limit, leave the request limit unspecified. This default is not
a hard cap on explicit values and does not estimate remaining context.

For a declared token-budget adapter, xhigh uses the high budget. Add the thinking
budget to the base output allowance, bounded by the model output ceiling. If the
result is no greater than the thinking budget, reduce that budget to the greater
of zero and the result minus the answer reserve. Effort-based adapters instead
use their declared level mappings. This does not require another bundled adapter.

Ordinary options include cancellation, optional temperature/output limit,
transport preference, cache preference, session affinity, request authentication,
string-valued headers and the two instrumentation callbacks. Provider-specific
wire fields, including tool choice and cache fields, require declared support.
They are never inferred from endpoint names. Do not add per-effort sampling
merges, provider environment overlays, context estimation or tokenizer services.
Unsupported optional preferences are not sent as unsupported wire fields; an
unsupported operation fails before dispatch.

### D07 — Flat reported usage and cost

Chat usage has input, output, cache-read, cache-write and total tokens. Input
excludes separately counted cache categories; reasoning already belongs to
output. Adapter normalization must not count reasoning or cache writes twice.
Always derive total = input + output + cache-read + cache-write from the
non-overlapping reported categories, rather than preserving an upstream total.
Initial zero counters mean no usage has been reported yet, not measured zero
consumption. Preserve valid reported usage on failure/abort.
Non-chat usage may remain absent; never manufacture measurements from content.

Flat rates are USD per million tokens for the four categories, with category
costs and their sum. No threshold tiers, separate reasoning costs or long-cache
subsets are added. Zero configured rates produce zero arithmetic estimates, not
proof of free access; callers must present pricing as unpriced/unknown rather
than a zero bill when rates were not supplied. Keep requested identity distinct
from actual response model and response ID.

The model module estimates cost, not account balance or total application spend.
If a tool separately invokes a model, the application can account for that
operation once without embedding usage in the tool-result transcript record or
adding it to main-conversation context usage.

### D08 — Transport policy and application retry ownership

The bundled connection defaults to two additional setup attempts after connection
failure, setup timeout, or an eligible HTTP response. `x-should-retry: true` or
`false` overrides status-based eligibility; otherwise 408, 409, 429 and 5xx are
eligible. Explicit cancellation always wins. Setting the retry count to zero
disables these retries. Request/auth construction failures are not retried.

Prefer a usable `retry-after-ms` value; otherwise accept `Retry-After` seconds
or an HTTP date. A nonnegative server delay is honored without a hidden cap;
an elapsed date means no wait. Malformed delays use the fallback in the defaults
table. Waits, including long server delays, are cancellable. Retry controls apply
only before a successful response body is consumed, never after partial content
or body failure. The adapter must not hide a fresh request inside one response.

The timeout bounds each transport attempt until response headers arrive. It is
not a body-idle or whole-operation deadline and is not reset by body chunks.
Omission selects the connection default; an explicit nonnegative millisecond
value overrides it. Zero means an immediate timeout, not disabled timeouts.
The model interface adds no default body-idle timeout or WebSocket connection.

Application retries are separate and visible. They may retry failed assistant
requests for transient overload/throttling/network or incomplete-stream errors,
but not authentication, billing/quota exhaustion or cancellation. Context overflow
belongs to compaction. Failed attempts remain in raw history but are omitted from
retry projection; completed tools are not rerun. Application retry start/end
events carry attempt/count, delay and safe failure information. Direct model
callers get ordinary failures without an imposed application retry controller.

### D09 — Selected-provider request authentication

A request supplies explicit auth or calls a narrow injected resolver for its
selected provider. That resolver returns request-scoped auth, or an explicit
configured-without-secret result for a local endpoint, plus a non-secret source
label if available. Missing auth and resolver failures use the operation's normal
failure contract. Only the selected, authorized adapter receives the credential.

Availability checks use metadata-only configured status, not request resolution.
The [engine credential owner](2026-10-05-engine-core.md#d09--settings-credentials-and-process-inputs)
handles precedence, expiry checking, refresh serialization, persistence, login
and secret commands. Provider descriptions may declare ambient credential names
as data. A provider adapter may expose an optional token-exchange/refresh operation
that the credential owner calls under its own lock; the bundled chat connection
implements no token exchange. Models never store credentials, lock refreshes or
choose credential precedence, and set no refresh deadline or early-validity window.
A request-auth fixture can exercise resolver outcomes without implementing
credential lifecycle here.

Provider/model string headers are overlaid by explicit request string headers,
case-insensitively. There is no nullable deletion map or final-header hook.
Secrets must not enter messages, ordinary logs, model events or error text.
Cancellation while waiting for auth prevents dispatch and returns aborted.

### D10 — Local catalogs and overrides

Catalogs are locally registered model entries. The application loads validated
local settings and supplies entries/overrides; models do not discover paths or
fetch catalogs. Invalid custom configuration reports an error without erasing
usable built-in/registered entries. Endpoint-only overrides retain the provider's
models. Model overrides are keyed by operation and model ID. Removing an override
restores the underlying registration.

Admitted provider registration/replacement/removal affects subsequent lookup and
dispatch immediately. Validation must complete before replacing usable data.
An already-dispatched request retains its captured adapter and metadata.
[Engine application policy](2026-10-05-engine-core.md#d02--consume-the-model-contract-coordinate-at-the-application)
reconciles the active selection with changed registrations; the model registry
never writes session preferences. Local reload means reading
local configuration, not remote refresh. There is no catalog store, network
snapshot, freshness timer, validator, publication generation or management retry.

### D11 — Admitted providers and two instrumentation hooks

`maestro-extensions` admits declared providers and supplies adapters to the model
interface. Ordinary extensions are separate programs; composition-wired built-ins
use the same registration surface in process. A registration declares identities,
local model metadata and implemented operations, with its request-auth integration.
Advertising an operation does not implement it. Initial registration precedes
startup selection. Runtime registration changes are distinct from reloading an
extension program, which remains restricted to between runs. Process launch and
permission policy stay outside models; process loss becomes a model failure.

The model interface accepts payload transformation before send and read-only
response status/header observation before body consumption. The host admits and
orders handlers. `before_provider_request` handlers run in registration order;
a replacement becomes the next input, while omission preserves the current
payload. `after_provider_response` observes status and headers, not body events.

Ordinary handler errors produce secret-safe extension diagnostics and continue
with the current payload/remaining handlers; cancellation still aborts the owning
operation. Sensitive hook values go only to admitted handlers, never ordinary
client events or durable records. There is no final-header transformation or raw
provider-event hook. Models implement callbacks and their request behavior, not
extension admission or separate-program transport.

### D12 — Classification and image generation

Classification accepts a JSON state object and named questions: choice with named
criteria, boolean with true/false criteria, or score with ordered criteria.
Answers preserve IDs and types: choice/probabilities/confidence, boolean
probability, or score/confidence. Validate missing, duplicate or mismatched
answers and malformed values; a score is not a probability. Optional positive
temperature applies only to capable adapters.

Image generation accepts ordered text/image inputs and returns ordered
text/image outputs, optional response ID and optional reported usage. Images are
base64 data with MIME type, not automatically fetched output URLs or files
written to disk.

Both return provider/protocol/model, timestamp and stop/error/aborted, with safe
failure text. Capability mismatch and missing auth fail rather than substituting
chat. Operation-specific lookup excludes these models from the chat picker.
These are native operation contracts exercised by the shared fake, not a mandate
to bundle a classifier, image provider or local-inference runtime.

### D13 — Embeddings and reranking

These native operations reuse identity, request auth/options, cancellation,
optional reported usage and terminal result conventions. They are not loop tools.

Embedding accepts ordered text inputs and returns one indexed result per input
with explicit representation and dimension metadata. Dense values are finite and
match the declared dimension. Missing, duplicate and out-of-range indices are
invalid. Representation identifiers remain data so additional sparse/multi-vector
forms need not change chat callers. Unsupported requested representations fail;
no dimension, normalization or truncation is assumed.

Reranking accepts a query and indexed candidate texts, returning every original
index exactly once with a finite relevance score. Normalize descending by score,
with original index breaking ties. Reject missing, repeated or out-of-range
indices. Scores are model-relative, not probabilities or cross-model comparable.
A caller can select leading results; there is no hidden top-k default.

Neither operation drops inputs, substitutes a model, fabricates scores or writes
a vector store. Provider limits are metadata, not universal batch sizes. Local
inference supplies its own later adapter; knowledge owns batching, retrieval
strategy and quality measurements.

### D14 — Scripted fake and dependency choices

The fake implements the same registered-provider interface. Scripts supply
queued responses or request-inspecting factories, explicit chunks, identities,
usage, errors and cancellation points. Calls and pending steps are observable;
exhaustion fails rather than replaying the last response. Extend this same fake
for all five operations, not a second inference protocol. Auth and transport
fixtures complement it without introducing remote catalog or deferred scripts.

Controlled clocks and supplied jitter values test outcomes, not elapsed wall
time. Reuse shared interface conformance instead of layering new internal mocks.
This specification adopts no library or version. Dependencies must stay within
existing owner approval. The bundled HTTPS transport still requires approval of
its TLS backend/features; a new randomness dependency would also require approval.
Any JSON Schema validation library also requires owner approval before adoption.
Those gates do not block the initial fake-only work.

## Defaults and limits

Defaults belong to the named owner, not to a whole run. Explicit supported request
values override their request defaults; settings locks apply at the application.

| Area | Default |
| --- | --- |
| Application selection | Automatic provider/model; global thinking `medium`; scope all available chat models. No per-model thinking preference store. |
| Sparse custom chat metadata | Name equals ID; reasoning false; text input; four zero price rates; context 128,000 and output 16,384 tokens. These are fallback metadata, not measured capacity. |
| Thinking budgets | Minimal 1,024; low 2,048; medium 8,192; high 16,384 tokens. Xhigh uses high where token budgets apply. Shared-ceiling answer reserve: 1,024 tokens. |
| Simple chat output | Explicit limit unchanged; otherwise `min(model output limit, 32000)` for a positive model limit; otherwise unspecified. No model-request context estimator or safety allowance. |
| Optional values | No default temperature or sampling overlay. Rates are USD per million tokens. |
| Transport/cache preference | Application transport `auto`; cache preference `short` (`none`, `short`, `long` are requests, not promised cache lifetimes). The bundled connection uses HTTP event streaming. |
| Bundled connection timeout | 600,000 ms per attempt until response headers; explicit zero is immediate, not disabled. No default stream-body idle or whole-operation timeout. |
| Bundled setup retries | Two additional attempts; zero disables retries. Server delays are uncapped and cancellable. Otherwise `min(500 × 2^i, 8000)` ms times `1 − u`, where `i` starts at zero and `u` is in `[0, 0.25)`. |
| Application retry | Defined by the [engine specification's application-retry default](2026-10-05-engine-core.md#defaults-and-limits), C10. |
| Credential lifecycle | No model-owned refresh window or timeout. The credential owner checks actual expiry; availability does not refresh. |
| Catalogs | Local registered data and supplied overrides only; no network startup, freshness interval or refresh deadline. |
| Additional operations | No universal embedding dimension, batch size, normalization, rerank top-k, provider-count cap or operation deadline. |

## Testing Decisions

Test through the highest useful public interface. Pure normalization tests may
sit within the owning module, but cannot replace caller-visible conformance.
Use synthetic public fixtures and deterministic scripts; no credentials, paid
provider calls, real waits or private data in the default suite. Run Linux now;
restore macOS and Windows checks before the first release. Current workspace
architecture/comment tests are prior art for executable conventions, not existing
model coverage: the model suite begins with the first text round trip.

## Out of Scope

1. Remote catalog refresh, persistent catalog snapshots, freshness/validator/publication machinery, management retries and a hosted catalog service.
2. System/tool-change transcript replay, named sections, nested tool-call records, constrained-sampling negotiation, image resize policies, per-model thinking preferences, `max` effort, tiered cost, expanded auth defaults, final-header/raw-event hooks and deferred model responses.
3. Credential storage/login/refresh coordination, settings-file formats and lock resolution, tool execution, session compaction, extension admission/transport and general RPC commands. Their neighboring owners consume the small interfaces above.
4. Local inference internals, GPU admission, speech, tokenizers, retrieval/batching/storage strategies, quality benchmarks and extra bundled provider packages.
5. Restartable-job scheduling, durable event delivery/replay, old-format readers, migrations, compatibility layers and external-agent execution. Dedicated jobs remain separate from model access.

## Further Notes

**Dependency gate.** Additional libraries and the concrete TLS backend/features
need owner approval before use. Do not infer backend approval from HTTP-client
approval. Do not delay fake-first work behind a network-only dependency.

**Documentation acceptance.** Every implementation ticket includes a Docs block:
public rustdoc; its feature page under `docs/`; necessary agent-facing rules or
terms in `AGENTS.md` or `CONTEXT.md`; and a `CHANGELOG.md` entry under
`[Unreleased]`. Strict rustdoc is mechanical; both review axes check the remaining
documentation and caller-independent adapter replacement.

**Ownership.** Models own model types/events. The application owns selection,
settings composition, local catalogs, retries and the SDK. Extensions own
admission; the agent owns execution; sessions own history/compaction; credentials
own persistence/refresh. Frontend libraries call the one application interface;
the binary composition root only wires adapters. MCP and restartable jobs remain
separate base capabilities, not imports of models.

### Glossary alignment

The glossary defines provider, model identity, operation, catalog, request,
attempt, model event and scripted fake. A catalog means locally registered
entries, not a remote discovery lifecycle. A provider implements model operations;
request authentication is supplied without giving it ownership of a credential
store. A model event is distinct from the agent event that wraps it; serialization
does not remove its partial snapshot.
