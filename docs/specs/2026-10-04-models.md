# Spec: models

Engine core, first piece. Lands on main before any code.

## Problem Statement

Users need to change model providers without losing usable conversation history, tool calls or visibility into failures and spending. Client and extension authors need one predictable contract instead of implementing provider-specific streaming, authentication and cancellation in every caller. Development and testing must work without credentials or paid requests.

## Solution

Maestro supplies one model interface with consistent messages, streaming events, usage and failure results. Registered providers support chat, classification, image generation, embeddings and reranking through replaceable adapters. Users can select configured models while preserving their session’s recorded choices.

The model module owns provider dispatch and request-time authentication. The application owns selection and visible retries; the extension host admits provider registrations; optional jobs own restartable scheduling. A scripted fake implements the same model interface so clients and the agent loop can be tested before live providers are connected.

## User Stories

### Select and understand a model
1. **US01.** As a user, I want to choose a configured model by provider and model name, so that I control which service receives my conversation.
2. **US02.** As a user, I want streaming and text, image, thinking and tool-call content represented consistently, so that changing providers does not change how I follow a conversation.
3. **US03.** As a user, I want supported thinking levels and per-model preferences, so that requests use the effort I selected without sending unsupported values.
4. **US04.** As a user, I want model changes restored with my session without overwriting startup preferences, so that resuming work preserves its context.
5. **US05.** As a user, I want truthful usage, cost, retry progress and cancellation, so that I understand spending and can stop waiting.

### Configure and extend access
6. **US06.** As a team lead, I want provider catalogs and model defaults controlled by layered settings, so that teams can customize permitted choices without bypassing locks.
7. **US07.** As an extension author, I want to register a provider with declared operations, so that new services need no changes to their callers.
8. **US08.** As an extension author, I want request-scoped credentials and cancellable authentication, so that my provider uses the selected account without owning the credential store.
9. **US09.** As an extension author, I want cached discovery and explicit catalog refresh, so that offline startup and a failed refresh retain useful model information.
10. **US10.** As a client author, I want one event and failure contract, so that my client handles built-in and extension providers consistently.

### Reuse the model seam
11. **US11.** As an agent, I want structured classification of supplied state, so that I receive typed answers rather than parsing conversational text.
12. **US12.** As an agent, I want image generation through a capable model, so that image-producing capabilities reuse ordinary provider access.
13. **US13.** As an agent, I want embeddings for ordered text inputs, so that knowledge capabilities can represent text without owning inference.
14. **US14.** As an agent, I want relevance scores for a query and candidate documents, so that retrieval can reorder candidates without owning inference.
15. **US15.** As a client author, I want a scripted fake provider, so that I can verify streaming, failures and recovery without credentials or paid requests.

## Implementation Decisions

### D01 — One deep model module

`maestro-models` invokes registered models. Its interface exposes provider registration, known/available model lookup, refresh, chat stream/completion, classification, image generation, embedding and reranking. Completion consumes the same chat stream; it is not a second implementation.
Provider adapters own wire conversion and supported operations. The bundled connection supplies configurable chat-completions access; additional services enter through extensions. An operation is callable only when its selected provider implements it; advertising a model does not create an implementation.
The crate accepts credential, catalog-store, transport and cancellation dependencies. It imports neither the application, frontends, extension host, MCP, jobs nor later-slice crates. Provider adapters and the scripted fake are modules at this core seam, not an agent framework. Embeddings and reranking use this same registry. `maestro-app` owns selection policy and settings composition; only the composition root wires dedicated capabilities into core interfaces.

### D02 — Registry and model identity

A model identity is the combination of provider ID, model ID and operation. The same upstream ID may therefore have distinct chat, classifier or image entries. Provider IDs, model IDs, endpoints and metadata are data, not closed provider lists in code.
Every entry carries its display name, operation, protocol identifier, endpoint, input capabilities and price metadata. Chat adds context/output limits, thinking support and optional level mappings, sampling parameters and cache metadata. Classifier entries declare context limits; image entries declare image output. Embedding and reranking metadata describe the representations and limits their implementation actually supports.
Known-model reads use the last published catalog and need no network. Available-model reads additionally check configured authentication and provider-specific account filtering; availability is not a claim that a live request will succeed. Ordinary chat selection excludes non-chat entries. A failing catalog getter contributes no models rather than crashing enumeration.

Model metadata may include `inputLimits`: maximum serialized request bytes, maximum images per message/request, and a cache-safe image resize profile with maximum width, height, base64 payload bytes and JPEG quality. Absent limits remain unspecified. Tool/application adapters consume preprocessing metadata; the model module does not become an image-processing implementation.

### D03 — Selection belongs to the application

Explicit selection wins. Otherwise, a new session uses its first scoped model, then its saved default, then an available provider-default model, then the first available model. A resumed session restores its recorded selection before using those fallbacks. A failed restoration reports the reason and chosen fallback.
Selection supports explicit provider/model references, exact IDs, name/ID matching, scoped patterns and a thinking suffix. Match a full model ID before parsing its final colon as thinking; slashes and colons can belong to IDs. For duplicate exact IDs, use the sole configured provider or report ambiguity. Fuzzy matching prefers an undated alias, then the latest sorted dated ID.
For an explicitly identified known provider, an unlisted model ID can use that provider’s base metadata with a visible custom-ID warning; it is not verified catalog information. An unknown provider or unresolved unqualified selection fails clearly. Scoped patterns produce diagnostics for unmatched entries and deduplicate matches.
A model change verifies configured authentication and records the selection. Only an explicit persist action changes startup defaults, subject to settings locks. Model persistence does not implicitly change the global thinking default. Provider-default preferences are catalog data, never selection branches naming individual providers.

### D04 — Messages and provider projection

The shared transcript contains system, user, assistant and tool-result messages with millisecond timestamps. System messages carry instruction text, named section changes and tool additions/removals. Public prompt/tool shorthand is normalized into system messages before provider dispatch.
User and tool-result content supports text and base64 images with MIME types. Assistant content supports text, thinking and tool calls. Tool calls carry identity, name, JSON-object arguments and optional provider replay metadata; tool results retain call identity, error state, optional JSON details and separately attributed usage. Tool execution remains outside this module.
Assistant messages retain requested provider/protocol/model, optional actual response model and response ID, requested/effective thinking metadata, usage, terminal reason and error text. Provider signatures are opaque; redacted thinking is never interpreted as readable text.
Provider projection preserves supported mid-conversation system/tool changes or collapses them into the leading system message. Cross-model projection removes foreign signatures, drops foreign redacted thinking, converts readable foreign thinking to text and normalizes tool-call IDs consistently with their results. Unsupported images become explicit omission text in the outgoing projection, not silent deletion from stored history. Missing tool results become error placeholders; failed/aborted assistant attempts do not re-enter model context as completed turns. Projection never edits the authoritative transcript.

A model-facing tool declaration contains `name`, `description`, JSON Schema `parameters` and optional `constrainedSampling`. Constrained sampling is disabled, a JSON-schema preference with `strict: prefer` or `require`, or a grammar declaration mapping protocol encoding identifiers to strings. Tool removal references contain `name`. Execution callbacks, display labels, output schemas, execution modes and recovery policy remain outside the model-facing declaration.

System `content` is text or text blocks. Later content appends instructions; ordered named `sections` replace values by name, with null removing a section. Apply `toolsRemoved` before `toolsAdded`; adding an existing name replaces its declaration. Public shorthand is `systemPrompt`, `messages` and `tools`; providers receive normalized `messages` only.

Tool-result messages retain `toolCallId`, `toolName`, text/image `content`, optional JSON `details`, optional separate `usage`, `isError` and timestamp. Optional `nestedCalls` records contain call ID, name, optional arguments or omitted-argument byte count, status (`ok`, `error`, `unfinished`), optional duration/error and an overall completeness flag. These records survive session serialization but are not sent to the model. Session orchestration owns their bounds.

### D05 — Streaming, failures and cancellation

A successful stream emits one `start`, balanced content-block start/delta/end events, then exactly one `done`. Event families are `text_*`, `thinking_*` and `toolcall_*`; every block event carries its content index and response-so-far. The terminal assistant message is authoritative. Empty successful responses still emit start and done.
Text/thinking start empty and grow through deltas; redacted thinking may arrive complete without deltas. Tool JSON can be incomplete during deltas but must be a parsed object by `toolcall_end`. Text fragments must preserve Unicode. Tool calls are not executable merely because a partial block exists.
Success reasons are `stop`, `length`, `toolUse` and, for a capable provider, `deferred`. `pending` is never terminal. A failure before generation may emit `error` without start; otherwise failure closes the started stream with `error`. Error reasons distinguish `error` from `aborted`, preserve valid partial content and include a useful, secret-safe message. No content or second terminal event follows termination.
The public model interface converts provider/auth/setup failures into that result contract, including adapter failures raised before a stream exists. Error categories distinguish catalog source/validation, provider capability, stream, authentication and token refresh. Cancellation reaches credential waits, requests, stream reads, discovery and retry sleeps; it is terminal and never automatically retried. Transport loss does not become a successful empty response.
Capable providers may return an opaque deferred handle containing provider, model, protocol, ID and optional expiry/poll hints/data. Fetch and best-effort cancellation use the same authentication seam. A handle is not proof that external work was cancelled. Restartable scheduling belongs to the optional, dedicated `maestro-jobs` module. The composition root connects it through application interfaces; `maestro-models` never imports it.

The model interface uses these event payloads: `start { partial }`; content starts `{ contentIndex, partial }`; content deltas `{ contentIndex, delta, partial }`; text/thinking ends `{ contentIndex, content, partial }`; `toolcall_end { contentIndex, toolCall, partial }`; `done { reason, message }`; and `error { reason, error }`, where `error` contains the terminal assistant message. Each payload also carries its event `type`. The content families are text, thinking and toolcall.

These are model-interface events, not the JSON/RPC wire representation. The loop wraps model updates as `message_update { message, assistantMessageEvent }`. JSON/RPC serialization replaces the outer cumulative message with cumulative `usage`, removes nested `partial`, and adds `id` and `toolName` to `toolcall_start`. It retains completed block values and terminal messages. The SDK retains the model-interface representation.

Application events include `thinking_level_changed`, `auto_retry_start` and `auto_retry_end`. Refresh returns results without adding a catalog RPC command.

### D06 — Thinking and request options

Supported levels are `off`, `minimal`, `low`, `medium`, `high`, `xhigh` and `max`. Non-reasoning models expose only off. Model mappings can explicitly disable levels; xhigh and max require explicit support. An unsupported request selects the next supported higher level, or the nearest lower level if none is higher; the effective choice is visible.
Explicit request effort wins over a scoped level, per-model preference and global startup default. Token-budget providers map xhigh/max to their high budget; effort-based providers use their own declared mapping. Thinking and answer tokens share the model’s output ceiling where required. Context estimation and output clamping do not claim tokenizer accuracy.
Requests accept cancellation, temperature, output limit, sampling parameters, transport/cache preference, session affinity, provider-scoped environment, headers and request instrumentation. Model sampling defaults are overlaid by effective-thinking settings, then request values. Optional wire fields apply only where the adapter supports them; a catalog capability is not inferred from an endpoint’s marketing label.

### D07 — Usage and cost

Chat usage records input, output, cache-read, cache-write and total tokens, plus optional reasoning and long-cache-write breakdowns. Reasoning is already part of output; long-cache-write is already part of cache-write. Neither subset is counted twice. Non-chat usage is optional when upstream does not report it.
Costs use catalog rates per million tokens, with separate categories and a total. A request-wide price tier applies only above its threshold, choosing the highest matching threshold using input plus cache reads/writes. Provider-specific long-cache pricing remains adapter/model policy. Preserve actual response identity when it differs from the requested model.
Catalog cost is an estimate, not a bill or account balance. Zero configured rates mean no priced cost is available, not proof that the service is free. Do not fabricate usage for non-chat responses. Tool-owned model calls stay separate from main-conversation context accounting; the application aggregates them once for spending.

### D08 — Retry ownership

Provider-request retries default to zero. If explicitly enabled, the adapter retries transport failures or eligible status responses during request setup, not after response content has begun; it honors explicit retry/no-retry headers and server retry delays. A delay above the configured cap fails immediately with the requested wait recorded. Backoff is cancellable. Do not hide a fresh request inside a partly emitted response.
The application separately retries failed assistant requests using its visible retry policy. Overload, transient throttling/network failure and incomplete upstream streams are retryable; authentication, billing/quota exhaustion and cancellation are not. Context overflow goes to session compaction, not transient retry. Failed attempts remain in raw history but are omitted from the retried model projection. Retrying a model request does not rerun completed tools.
`auto_retry_start` reports attempt, maximum retries, delay and error; `auto_retry_end` reports success/failure, completed attempt count and optional final error. Normal model errors remain available to direct library callers, without imposing application retries on every operation.

### D09 — Request-time credentials

All operations resolve credentials through the owning provider. Explicit request credentials take precedence, then stored credentials, configured provider credentials and ambient provider sources. A stored credential owns that provider: failed token refresh or an unsupported stored credential type never silently switches accounts via ambient credentials.
A provider declares API-key/ambient and/or refreshable-token methods, including a configured-without-secret result for local services. Credential checks can avoid refresh and command execution; request resolution performs needed work. The injected store supplies read, metadata-only list, serialized modify and delete, keyed by provider ID. Concurrent refresh rechecks current credentials under that serialization before rotating them.
Provider resolution supplies request auth, optional endpoint/environment and a non-secret source label. Model and explicit request headers overlay defaults case-insensitively; a null header removes the corresponding default. The final header transformation runs once. Preserve the stored credential on refresh failure. Only the selected, authorized provider receives its request credentials; secrets never enter transcripts, ordinary logs or general event records. Storage, login interaction and cross-process locking implementation are owned elsewhere.

### D10 — Catalog refresh

Begin with bundled/registered entries and stored snapshots. Restore cache before network authentication. Explicit refresh may select providers, permit network access, force freshness bypass and supply cancellation; it returns an aborted flag and provider-keyed errors without making one provider’s failure erase others.
Provider refresh chooses ephemeral publication, persisted replacement or persisted deletion. The catalog store holds entries plus optional last-modified, checked-at and entity-tag metadata. Publication is serialized and generation-checked; replacement, removal or a newer refresh invalidates late publication from an older registration. Failed refresh retains the previous usable list.
A configured remote catalog overlays entries by operation and model ID, retains offline data and uses validators only with a cached body. A not-modified response advances freshness without losing entries. Custom endpoint/model overrides apply above the provider; endpoint-only overrides preserve its catalog. Removing an extension override restores the underlying provider.
Refresh never silently switches the selected model or rewrites an in-flight request. Network/offline policy comes from the application. No new catalog-hosting service or mandatory external catalog URL is introduced by this section.

### D11 — Extension providers and instrumentation

`maestro-extensions` admits declared provider registrations and presents them as adapters to `maestro-models`. Ordinary extensions are separate programs; composition-wired built-in extensions use the same registration interface in-process. A registration declares identity, models, supported operations, authentication methods and optional filtering/refresh behavior. Caller-facing contracts are identical to bundled providers; unsupported operation/model combinations fail before sending a request.
Initial provider registration completes before startup model selection. Admitted runtime provider registration, replacement and removal take effect immediately within the extension’s declaration; they are not extension-process reloads. They invalidate superseded catalog publication without rewriting an already-dispatched request or silently changing session selection. Extension-process reload remains restricted to between runs. The model crate owns neither process launch nor permission policy. A provider-process failure becomes a model error, not an engine crash.
Instrumentation permits payload transformation before send, final-header transformation, response status/headers before body consumption, and read-only observation of parsed provider events before normalization. Only admitted hooks receive those sensitive views; these are not automatically public or durable events. Raw provider events are adapter-owned, not a second normalized protocol.

Provider instrumentation handlers run in registration order. A `before_provider_request` reply may supply a replacement payload; omission keeps the current payload. A separate-program `before_provider_headers` reply may supply the complete replacement header map; omission keeps the current map, and null-valued headers suppress the corresponding defaults. The host applies each replacement before invoking the next handler. The in-process adapter exposes the same resulting transformation.

`after_provider_response` and `provider_stream_event` are observations, not request transformations. Ordinary handler errors produce extension diagnostics and dispatch continues, matching these hooks’ error policy; they do not acquire tool-call blocking semantics. Cancellation still cancels the owning operation. Sensitive hook payloads are confined to admitted handlers and are not published as ordinary client events.

### D12 — Classification and image generation

Classification accepts a JSON state object and named questions: choice with named criteria, boolean with true/false criteria, or score with ordered criteria. Answers retain question IDs and types: choice/probabilities/confidence, boolean probability, or score/confidence. A score is not interchangeable with a probability. Optional positive temperature applies only to capable adapters.
Image generation accepts ordered text/image inputs and returns ordered text/image outputs, optional response ID and optional usage. Generated images are returned as base64 data with MIME type, not automatically written to disk or fetched from arbitrary output URLs.
Both operations return provider/protocol/model, timestamp and `stop`, `error` or `aborted`, with error text on failure. Capability mismatch and missing credentials return failure results, not invented chat substitutes. These models are discoverable through operation-specific access, not the chat picker. The local inference program’s narrower modality choices do not restrict other registered providers.

### D13 — Embeddings and reranking

Embedding and reranking are additional model operations, not tools built into the loop. Their interface reuses provider identity, request auth/options, cancellation, optional usage and terminal result conventions.
Embedding takes an ordered collection of text inputs. A successful result returns one indexed embedding per input, with explicit representation and dimension metadata; a dense representation contains finite numeric values of the declared dimension. Representation identifiers and capability metadata are data, allowing a provider to describe additional sparse or multi-vector forms without changing chat callers. No dimension, normalization or truncation is assumed; unsupported requested representations fail explicitly.
Reranking takes a query plus indexed candidate texts and returns each candidate’s original index and finite relevance score. The normalized result is descending by score, with original index breaking ties. Scores are model-relative, not probabilities or cross-model comparable values. Missing, repeated or out-of-range indices are invalid results; caller-side selection can take the first results without a hidden top-k default.
Neither operation silently drops inputs, replaces models, invents scores or performs vector-store writes. Model limits come from declared metadata, not a universal batch size. The local inference program implements its adapter in its own slice; knowledge packages own batching, retrieval strategy and quality measurements.

### D14 — Scripted fake and dependency choices

The fake implements the same provider interface. Tests supply queued responses or request-inspecting response factories, explicit content chunks, identities, usage, errors and cancellation points. Script exhaustion fails rather than repeating a response. Calls and pending steps are observable; scripts can exercise discovery, auth, deferred handles and every supported operation without external I/O.
Deterministic scripts and controlled clocks test behavior, not elapsed wall time. Shared tests reuse this module rather than mocking the loop’s internal functions. This specification selects no new library or version. Implementation may use dependencies within their existing approval scope; additional dependencies remain pending owner approval through the shared capability proposal.

## Defaults and limits

These defaults apply only to the named operation or owning module; they are not whole-run budgets.

| Area | Default |
| --- | --- |
| Application selection | Automatic provider/model; thinking `medium`; no per-model overrides; scope all available chat models. |
| Sparse custom chat metadata | Display name equals ID; reasoning false; text input; four price rates zero; context window 128,000; output limit 16,384. These are fallback metadata, not measured endpoint capacity. |
| Thinking budgets | Minimal 1,024; low 2,048; medium 8,192; high 16,384 tokens. Extended levels use the high token budget where applicable. Shared-ceiling adjustment reserves 1,024 answer tokens. |
| Simple-request output | Start with the requested output limit or model output limit. For positive context windows, clamp against estimated remaining context after a 4,096-token safety allowance, with at least one available output token. |
| Estimation | Four UTF-16 code units per token, rounded up; each image contributes 4,800 units. Prefer applicable reported usage plus estimated trailing content. This is not tokenizer accuracy. |
| Optional request values | No default temperature, sampling override or additional request token cap. Cost rates are USD per million tokens. |
| Transport/cache | Application transport `auto`; cache retention `short`; an undeclared cache lifetime is unknown. |
| Timeouts | HTTP header/body idle 300,000 ms; zero disables it. Provider timeout inherits that value unless overridden; disabled inherited idle maps to 2,147,483,647 ms. Capable WebSocket adapters use a 15,000-ms handshake timeout; zero disables it. |
| Provider retry | Zero additional attempts. Server-delay cap 60,000 ms; zero disables the cap. When enabled, fallback delay is `min(500 × 2^retryIndex, 8000)` ms multiplied by `1 − uniform[0, 0.25)`, with retryIndex starting at zero. |
| Application retry | Enabled; three additional attempts; delay `min(2000 × 2^(attempt−1), 60000)` ms, without jitter, with attempt starting at one. |
| Request credential refresh | Refresh at five minutes or less remaining validity; refresh timeout 15,000 ms. Callers may require longer validity. Catalog-only refresh instead checks expiry. |
| Catalog initialization | Restore cache before network authentication. Application creation is cache-only unless network refresh is explicitly enabled. Low-level explicit refresh permits network by default; force defaults false; omitted provider selection means all refreshable providers. |
| Configured remote catalog | Freshness four hours; each HTTP attempt 4,000 ms; two additional immediate management retries. This policy is not inherited by generation requests. |
| Application catalog wait | RPC background refresh has a 15,000-ms caller deadline. The generic model runtime introduces no default overall refresh deadline or periodic timer. |
| Deferred responses | Fetch wait zero performs one status check. Other polling/expiry information comes from the provider handle. |
| Additional operations | No universal embedding dimension, batch size, normalization, rerank top-k, provider-count cap or whole-operation deadline. |

## Out of Scope

1. Local inference internals, GPU admission/loading, speech, tokenizer services and retrieval-model selection or benchmarks.
2. Credential persistence technology, login commands/dialogs, settings-file layout and lock resolution; those use the shared contracts above.
3. Tool execution, compaction policy, restartable-job scheduling, extension transport and general RPC commands belong to neighbouring modules. Durable event records, cross-process event delivery, subscriber cursors and event replay are outside the entire engine-core slice.
4. Retrieval pipelines, vector/graph stores, account balances/quotas and provider packages beyond this slice’s configurable connection and registration surface.
5. Old-format readers, migration layers, external-agent execution and a new hosted model-catalog service.

## Further Notes

**O01 — Additional dependency approval.** Obtain approval before adopting dependencies outside the existing approved foundation. This does not block model-interface and scripted-fake tickets that stay within existing approvals.

`maestro-app` owns selection, settings composition, visible retries and the SDK. `maestro-extensions` admits provider registrations; `maestro-agent` executes the loop; `maestro-session` maintains conversation history and compaction; `maestro-cli` adapts chat, print, JSON and RPC modes; `maestro-credentials` persists credentials. Optional `maestro-jobs` owns restartable scheduling and is connected only by the composition root.

### Glossary terms for `CONTEXT.md`

**Provider:** A registered adapter that supplies models, implements declared operations and resolves its request authentication.  
**Model identity:** The combination of provider ID, model ID and operation.  
**Operation:** A kind of model work: chat, classification, image generation, embedding or reranking.  
**Catalog:** The published collection of model entries with their identities, capabilities and price metadata.

**Request:** An invocation of a selected model operation with its inputs, options, authentication and cancellation.  
**Attempt:** One try at fulfilling a request; failed assistant attempts remain in raw history but are omitted from retry projection.  
**Model event:** An ordered update or terminal outcome emitted by a model stream, distinct from its JSON/RPC projection.  
**Scripted fake:** A provider adapter driven by queued responses or request-inspecting factories, with observable calls and no external I/O.
