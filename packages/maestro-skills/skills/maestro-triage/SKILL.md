# Triage a request with the maintainer

Use the [tracker](../../references/issue-tracker.md) and its repository-specific role
mapping. Pull/merge-request discovery is disabled by default. When enabled, discover
external authors only; an explicitly named request can come from any author. Read its
diff as well as the discussion. Resolve ambiguous issue/request identifiers through
the tracker's rules rather than assuming both number spaces work alike.

Every issue or comment posted during triage starts with this exact disclosure:

> *This was generated by AI during triage.*

## Roles and transitions

Categories are `bug` (broken behaviour) and `enhancement` (new or improved behaviour).
State roles are `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human` and
`wontfix`. Every triaged request has exactly one category and one state. Follow the
mapped labels; create a missing mapped label rather than a competing scheme.

An unlabeled request normally enters needs-triage, then moves to needs-info, either
ready state or wontfix. Reporter activity returns needs-info to needs-triage. Conflicting
state roles or unusual transitions need maintainer direction before proceeding.
For attached code, ready-for-agent means an agent has a brief for work remaining;
ready-for-human means a human should handle the next step or merge judgment.

## Show attention buckets

Present unlabeled requests, needs-triage requests and needs-info requests with reporter
activity after the last triage notes, oldest first in each bucket. Include counts and
one-line summaries. Mark issue versus request when requests are enabled. External-author
filtering applies only to discovery. Let the maintainer choose what to examine.

## Triage the selected request

1. Read body, comments, labels, author, dates and prior triage notes; for a request,
   read the diff too. Read glossary and relevant ADRs. Search implementation by domain
   concept for already-built behaviour and search [prior rejection](OUT-OF-SCOPE.md)
   by meaning. Report where you looked, not just whether keywords matched.
2. Recommend category and state with reasons and relevant code context. Wait for the
   maintainer's direction before applying the recommendation.
3. Verify before grilling. Use `/skill:maestro-diagnose` for claimed failures, reproducing
   reporter steps. Check a request's supplied diff and relevant tests. Report confirmed
   with the path, failed, or insufficient detail. Missing detail supports needs-info.
4. If the request needs sharpening, use `/skill:maestro-grilling` and
   `/skill:maestro-domain-modeling`, one `ask_user_question` call per interview round.
   Update settled vocabulary and durable decisions; never repeat answered questions.
5. Apply the directed outcome below, with the disclosure on every post.

## Outcome

For ready-for-agent, post an [agent brief](AGENT-BRIEF.md). For ready-for-human, use
the same structure and explain the human judgment, access or testing needed.
For needs-info, post notes with 'What we have established' and 'What we still need
from the reporter'. Preserve settled facts and ask specific, answerable questions.
For needs-triage, apply the role and optionally record useful partial progress.

For wontfix, distinguish:

- Already implemented: link where it exists and close, without a rejection record.
- Rejected bug: explain respectfully and close, without a rejection record.
- Rejected enhancement: create or extend the concept's out-of-scope record, link it
  from the explanation and close. This applies equally to attached code.

A direct maintainer override skips grilling. Confirm the role changes, comments or
closure you will perform, apply their direction and offer a brief when needed.
On resumption, read prior notes and later reporter replies, present the updated state
and ask only unresolved questions.
